# ADR-0041 打开交接收成一个 module

状态：已接受

## 背景

点开一个网络视频，到真正出声，中间要等一会儿：目录读出来、网络探测回来、播放页画好、画面就绪。这段时间里应用得记着「走到哪一步了」，得计时（太久没接手就退回列表），还得保证「只起播一次」。

这几件事现在被拆成几个小类，真正的编排写在界面层：起表、停表、四条前置条件、兜底、失败回滚、退后台暂停计时，都在一个方法里手写。

问题不在于哪一处写错，而在于「谁先谁后」只活在界面的代码顺序里。比如「起播成功了才算接手」这条，成立的前提是起播函数刚好是同步的；它哪天变成需要等待的调用，界面就会停在「等待接手」，只剩返回键能按。这类顺序没有测试，因为整条链没有一个入口能在单元测试里跑起来。

## 决策

- 一个 module `OpeningHandover` 接手：入口阶段、代际、兜底计时、待起播请求与起播握手。原先负责这三件事的小类并入，不再保留。
- 对外只给这些：开始打开、准备完成、尝试接手、时间推进、前后台变化、离开播放页、取消。
- 起播通过注入的一个函数完成：入参是播放列表、当前项、代际与目录，返回值表示控制层是否接受。module 不认识播放控制层的类型。
- 接手标记与起播在同一个调用里完成，界面层不再自己写「已接手」。顺序由结构保证，不靠调用方记得。
- 时间由外部推进：module 只算账，不自带协程。
- 兜底时限、只在等待接手阶段累计、只在前台累计、失败与取消直接清空阶段与代际，沿用 ADR-0038，本决策不改这些取值。
- 收尾动作仍由界面决定：提示什么、回滚到哪、是否退出播放页。module 只给结论。

## 后果

- 「点开 → 准备 → 等待 → 接手 → 首个就绪」整条链可以在纯 JVM 测试里跑完，不需要界面。
- 新增一种打开路径时，只多一个入口事件，不必在界面层再复制一段循环。
- 代价：几件小事并成一个较长的类，读的时候要在一个文件里跨小节看。
- 代价：起播函数由界面注入，注错了 module 会把它当成「控制层不接受」。接线由界面负责，module 不校验。
